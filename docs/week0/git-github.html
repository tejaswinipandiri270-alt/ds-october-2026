1What version control is, and why you need it

Intuition. Version control is an unlimited, labelled "undo history" for a whole project folder, which several people can share without overwriting each other's work.

Without version control, projects end up looking like this:

model.ipynb
model_v2.ipynb
model_v2_final.ipynb
model_v2_final_REALLY_final.ipynb
model_v2_final_alex_edits.ipynb

Nobody knows which file is current, what changed between them, or who changed it. A version control system (VCS) solves this. It records every saved state of your project as a snapshot, with a note saying who made it, when, and why. You keep one copy of each file, and the history lives alongside it.

What it gives you

A safety net

Go back to any earlier version of any file. Broke something that worked yesterday? Compare against yesterday's snapshot and see exactly which lines changed.

A history with reasons

Each snapshot carries a message such as "Fix leakage in train/test split". Months later you can find out why a line exists.

Safe experiments

Try a risky idea on a separate branch. If it fails, throw the branch away; the working version is untouched.

Collaboration

Several people edit the same project at the same time. Git combines their work and flags the rare places where two people changed the same lines.

Git is by far the most widely used version control system. It is free, open source, and was created by Linus Torvalds in 2005 to manage the Linux kernel. It is distributed: every copy of a repository contains the full history, so you can commit, browse history and create branches with no internet connection.

Data scientists need it too. Notebooks, scripts, SQL, configuration, prompts and agent code all change constantly. Employers expect you to use Git, and your GitHub profile is often the first thing a hiring manager looks at.

3One-time setup

In short. Install Git, tell it your name and email (stamped on every commit), pick sensible defaults, and connect it to your GitHub account. You do this once per computer.

1. Install Git and check it works

SystemHow to install
macOSRun xcode-select --install (Apple's command-line tools include Git), or brew install git if you use Homebrew
WindowsInstall Git for Windows from git-scm.com. It includes Git Bash (a terminal where all the commands on this page work) and Git Credential Manager
Linux (Debian / Ubuntu)sudo apt install git
 
git --version          # e.g. git version 2.4x.x  (any recent version is fine)

2. Tell Git who you are

Every commit records an author name and email. Use the email linked to your GitHub account so your commits appear on your profile. (GitHub's email settings also offer a private …@users.noreply.github.com address if you prefer not to publish your real one.)

git config --global user.name "Alex Smith"
git config --global user.email "alex.smith@example.com"

--global means "for every repository on this computer, for my user". Without it, the setting applies only to the repository you are in.

3. Sensible defaults

# Call the first branch of new repositories "main" (GitHub's default) instead of "master"
git config --global init.defaultBranch main

# When git pull finds that you and the remote have both moved on, combine them with a merge
# (without this, recent Git versions stop and ask you to choose)
git config --global pull.rebase false

# Optional: use VS Code instead of Vim when Git needs you to type a message
git config --global core.editor "code --wait"

# Check what you have set
git config --global --list

Stuck in Vim? If you run git commit without -m (or Git opens an editor during a merge) you may land in Vim, which confuses everyone the first time. Press Esc, type :wq and press Enter to save and quit. Type :q! instead to quit without saving (which aborts a commit).

4. Connect to GitHub

Create a free account at github.com if you don't have one. GitHub no longer accepts your account password for Git commands, so you need one of these:

MethodHowNotes
GitHub CLI (easiest)Install gh, then run gh auth login and follow the prompts in your browserSets up HTTPS authentication for Git automatically
Git Credential ManagerComes with Git for Windows; available for macOS and LinuxThe first git push opens a browser window to sign in; the credential is then stored securely
SSH keyGenerate a key with ssh-keygen -t ed25519 and add the public key in GitHub → Settings → SSH and GPG keysThen use the git@github.com:… form of repository URLs

Never paste tokens, passwords or keys into code, notebooks or chat. Let the credential helper store them for you.

5The three areas (plus the remote)

Intuition. Think of packing a parcel. You make things (working directory), put the ones you want in the box (staging area), seal and label the box (commit), and post it (push). Pull is receiving a parcel.

The first three areas are all on your laptop. Only push, pull, fetch and clone talk to GitHub. A very common beginner surprise: a commit is not on GitHub until you push it.

Why have a staging area at all? It lets you build a commit deliberately. If you fixed a bug and reformatted an unrelated file, you can stage and commit them separately, so each commit does one thing.

7Branches, and why you never work on main

    
Intuition. A branch is a parallel line of work. main is the version everyone trusts; a branch is your private workspace. Under the bonnet a branch is just a sticky label pointing at a commit, so creating one is instant and costs nothing.


    
Why not commit straight to main?

    
    
      
  • main should always work. Others pull from it and build on it. Half-finished work there breaks things for everyone.
    • 
      
  • Review. Work on a branch can be reviewed in a pull request before it reaches main.
    • 
      
  • Isolation. You can keep several pieces of work separate (a bug fix and an experiment) and switch between them.
    • 
      
  • Easy to abandon. A failed experiment is one git branch -D away from disappearing; main never saw it.
    • 
      
  • Syncing stays simple. On this course, keeping your fork's main identical to the course repository's main makes syncing trivial. Your work lives on week1/alex, week2/alex and so on.
    • 
    


    
Branch commands


git branch                      # list local branches; * marks the current one
git branch -a                   # also list remote-tracking branches (remotes/origin/...)
git switch -c week1/alex        # create a new branch from where you are AND switch to it
git checkout -b week1/alex      # the older command that does exactly the same thing
git switch main                 # switch to an existing branch (older: git checkout main)
git branch -d week1/alex        # delete a branch that has been merged
git branch -D experiment        # force-delete a branch, even if it is not merged
git push -u origin week1/alex   # first push of a new branch; -u sets its upstream

    
switch vs checkout. git checkout does many unrelated jobs (switching branches, restoring files, and more), which made it confusing. Git 2.23 (2019) added two clearer commands: git switch for branches and git restore for files. Both styles work; you will see checkout in older tutorials and Stack Overflow answers.

    
Switching branches changes your files. When you switch, Git rewrites the working directory to match the other branch. Uncommitted changes come with you if they don't clash; if they would be overwritten, Git refuses. Commit first, or put them aside with git stash and bring them back later with git stash pop.

Fast-forward vs merge commit

    

      
Fast-forward
If main has not moved since the branch was created, there is nothing to combine: Git just slides the main label forward to the branch's latest commit. No new commit, perfectly straight history.

      
Merge commit
If both branches have new commits, Git creates a merge commit with two parents that combines both lines of work. If the same lines were changed on both sides you get a conflict to resolve.

In short. A pull request (PR) is a GitHub page that says "please merge my branch into that branch", with the changes shown line by line so others can review and discuss them before they are merged.


    
Pull requests are a GitHub feature, not a Git command. (GitLab calls them merge requests.) They are how almost every team gets code into main: nothing reaches main without someone else looking at it first.

10Keeping your fork in sync

    
In short. Your fork is a snapshot taken on the day you forked. When the trainers add next week's material to the course repository, your fork does not update by itself. You pull the new commits in.


    
Option A: the "Sync fork" button, then pull

    
    
      
  1. Open your fork on GitHub, on the main branch.
    2. 
      
  2. If it is behind, GitHub says "This branch is N commits behind samuelts96/ds-october-2026:main". Click Sync fork → Update branch.
    3. 
      
  3. Your fork on GitHub is now up to date. Bring your laptop up to date:
    4. 
    


git switch main
git pull                      # pulls from origin/main, your freshly synced fork


    
Option B: the command line, with the upstream remote


git switch main

git merge upstream/main       # bring them into your local main (usually a fast-forward)
git push origin main          # update your fork on GitHub too

Why syncing is painless here: you never commit to your own main, so it never diverges from the course's main. Every sync is a simple fast-forward with no conflicts.

  


  
  

    
11Merge vs rebase

    
Intuition. Both bring the changes from one branch into another. Merge ties the two histories together with a knot (a merge commit) and keeps the history exactly as it happened. Rebase lifts your commits off and replays them on top of the other branch, as if you had started your work later; the history is straighter but rewritten.


    

      
Compare: merge vs rebase

      
Your branch feature started at B and has commits C and D. Meanwhile main gained E and F.

      

        
        
        
      

      

      

      

    



# Merge: bring main into your branch (safe, never rewrites history)
git switch week1/alex
git merge main

# Rebase: replay your branch's commits on top of the latest main (rewrites them)
git switch week1/alex
git rebase main
# if there are conflicts: fix the file, git add it, then
git rebase --continue          # or give up and go back:  git rebase --abort


    

      
MergeRebase

      
        
HistoryTrue record of what happened, with merge commits; can look tangledStraight line; looks as though the work happened in sequence

        
Rewrites commits?NoYes: your commits get new IDs (C becomes C′)

        
ConflictsResolved once, in the merge commitMay have to be resolved commit by commit

        
After pushingNormal git pushNeeds a force push if the branch was already pushed

        
Use whenCombining shared branches; whenever in doubt; the default for this courseTidying your own branch before a pull request, when nobody else uses it

      
    


    
The golden rule of rebasing: never rebase commits that other people may have based work on, which means never rebase main or any branch someone else has pulled. Rebasing replaces commits with new ones; anyone holding the old ones ends up with duplicated, tangled history.


    
Force pushing safely: --force-with-lease

    
After rebasing a branch you have already pushed, a normal push is rejected because the remote has commits (the old C and D) that are no longer in your branch. You have to overwrite the remote branch:


git push --force-with-lease    # overwrite the remote branch, but ONLY if it is still where
                               # you last saw it (nobody has pushed anything new since)

    
Plain git push --force overwrites unconditionally and can silently delete a teammate's commits. --force-with-lease refuses if the remote has changed since your last fetch. Use force pushes only on your own branches, never on main.

  


  
  

    
12Merge conflicts

    
In short. A conflict happens when two branches changed the same lines of the same file and Git cannot know which version you want. It stops, marks the spot, and asks you to decide. It is normal, not an error.


    
Changes to different files, or to different parts of the same file, merge automatically. Only overlapping edits conflict. When one happens during git merge or git pull, Git prints:


Auto-merging config.py
CONFLICT (content): Merge conflict in config.py
Automatic merge failed; fix conflicts and then commit the result.

    
and git status shows:


On branch week1/alex
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   config.py


    
Reading the conflict markers


<<<<<<< HEAD
TEST_SIZE = 0.25                  <- your version (the branch you are on)
=======
TEST_SIZE = 0.2                   <- the incoming version (the branch being merged in)
>>>>>>> main

    
    
      
  • <<<<<<< HEAD to =======: what your current branch has.
    • 
      
  • ======= to >>>>>>> main: what the other branch has.
    • 
      
  • Everything outside the markers merged cleanly.
    • 
    


    

      
Try it: resolve a conflict

      
You ran git merge main on week1/alex. You changed the test size; the trainers changed it too and added a validation size. Choose a resolution.

      

        
        
        
        
      

      

      

    


    
How to resolve

    
    
      
  1. Run git status to see which files conflict.
    2. 
      
  2. Open each file. Find the markers (VS Code highlights them and offers "Accept Current", "Accept Incoming" and "Accept Both" buttons).
    3. 
      
  3. Edit the file into the version you want and delete all three marker lines.
    4. 
      
  4. Run the code or tests to check it still works.
    5. 
      
  5. Mark it resolved with git add config.py.
    6. 
      
  6. Finish the merge with git commit (Git prepares the message; save and close the editor), or git merge --continue.
    7. 
      
  7. git push.
    8. 
    

    
Changed your mind? git merge --abort puts everything back exactly as it was before the merge. During a rebase, use git rebase --abort. Nothing is lost.

    
Notebooks conflict badly. A .ipynb file is JSON that includes outputs and execution counts, so two people running the same notebook "change" it even if nobody edited the code. Avoid two people editing the same notebook; clear outputs before committing; move reusable code into .py files.

  


  
  

    
13Undoing things

    
In short. Almost anything that has been committed can be recovered. The dangerous commands are the ones that throw away changes that were never committed, and the ones that rewrite history other people already have.


    

      
SituationCommandEffectRisk

      
        
I staged a file by mistakegit restore --staged file.pyUnstages it; your edits stay in the working directorysafe

        
I want to throw away my edits to a filegit restore file.pyPuts the file back to its last staged/committed versionedits lost for good

        
Typo in my last commit message, or I forgot a file (not pushed yet)git add forgotten.py
git commit --amend -m "Better message"		Replaces the last commit with a corrected onerewrites 1 commit

        
Undo a commit that is already pushed or sharedgit revert <commit-id>Adds a new commit that does the opposite. History is keptsafe

        
Undo my last commit but keep the changes staged (not pushed)git reset --soft HEAD~1Moves the branch back one commit; changes stay stagedrewrites history

        
Undo my last commit, keep the changes unstagedgit reset HEAD~1Same, but changes go back to the working directory (--mixed, the default)rewrites history

        
Throw away my last commit and all uncommitted changesgit reset --hard HEAD~1Branch, staging area and files all resetdestroys work

        
Put work aside to switch branchesgit stash … git stash popSaves uncommitted changes on a stack and cleans the working directorysafe

        
I committed a file that should be ignoredgit rm --cached .envStops tracking it but leaves it on disk; add it to .gitignore and commitsafe

        
I lost a commit after a reset or rebasegit reflogLists everywhere HEAD has been; git switch -c rescue <id> brings it backsafe

      
    

    
HEAD~1 means "one commit before HEAD"; HEAD~3 means three before. Commit IDs come from git log --oneline.


    
revert vs reset

    

      
git revert: undo by adding
  • Creates a new commit that cancels an old one
  • History is not rewritten, so it is safe on pushed and shared branches
  • Use it for anything already on GitHub

      
git reset: undo by moving back
  • Moves the branch label to an earlier commit; later commits drop off the branch
  • Rewrites history: pushing afterwards needs a force push
  • Only for local commits that nobody else has
  • --hard also deletes uncommitted changes, with no undo

    

    
Before any --hard or git restore file, run git status and git diff. Uncommitted changes are not in Git's history, so even git reflog cannot bring them back.

  


  
  

    
14.gitignore for Python and data science

    
In short. .gitignore is a text file listing files and folders Git should pretend not to see. Use it to keep out secrets, big data, generated files and virtual environments.


    
Create a file named exactly .gitignore in the top folder of the repository and commit it. Each line is a pattern:


# --- Python ---
__pycache__/
*.py[cod]
.venv/
venv/
*.egg-info/
.pytest_cache/

# --- Jupyter ---
.ipynb_checkpoints/

# --- Secrets: NEVER commit these ---
.env
*.pem
*.key

# --- Data and outputs (often large, sometimes confidential) ---
data/*
!data/.gitkeep
*.parquet
*.pkl
models/

# --- Experiment tracking ---
mlruns/
mlartifacts/
wandb/

# --- Editors and operating systems ---
.vscode/
.idea/
.DS_Store
Thumbs.db


    

      
PatternMatches

      
        
.envA file or folder named .env in any folder

        
mlruns/A folder named mlruns anywhere (trailing / = folders only)

        
*.pklAny file ending in .pkl

        
/output.csvOnly output.csv in the top folder (leading / anchors to the repository root)

        
data/* then !data/.gitkeepEverything inside data/ except an empty placeholder file, so the folder still exists in the repository. (! re-includes a file, but it cannot re-include anything inside a folder that is itself ignored with data/; that is why data/* is used.)

        
# commentIgnored line

      
    


    
    
      
  • Why ignore .venv? A virtual environment holds thousands of installed package files and only works on the machine that created it. Commit requirements.txt (or pyproject.toml) instead, so others can rebuild it.
    • 
      
  • Why ignore data? Datasets can be large or confidential. GitHub warns about files over 50 MB and blocks files over 100 MB. Document where the data comes from in the README instead.
    • 
      
  • Why ignore mlruns/? MLflow writes a run folder for every experiment; it grows quickly and belongs in a tracking server, not in Git.
    • 
    

    
.gitignore only affects files Git is not already tracking. If you committed .env before ignoring it, run git rm --cached .env, commit, and push. GitHub also publishes ready-made templates at github.com/github/gitignore (for example Python.gitignore), and offers one when you create a repository.

  


  
  

    
15Good practice

    
In short. Commit small and often, write messages your future self will thank you for, keep secrets out, and pull before you push.


    
Small, focused commits

    
One commit = one logical change: "Add missing-value imputation", not "Monday's work". Small commits are easier to review, easier to understand later, and easier to revert on their own. Commit whenever you reach a point that works, even partly.


    
Good commit messages

    
Write the subject line in the imperative mood, as if giving an order: "Add", "Fix", "Remove", not "Added" or "Fixes". A handy test: the line should complete the sentence "If applied, this commit will…". Keep it to about 50 characters, with no full stop. If more explanation is needed, leave a blank line and write a body (use git commit without -m, or several -m flags).

    

      
PoorBetter

      
        
updateAdd stratified split to training script

        
fixed stuffFix data leakage from scaling before the split

        
asdfghRemove unused plotting helpers

        
Changes made to the notebook for the week 1 exercises on classification.Complete week 1 classification exercises

      
    


    
Never commit secrets

    
API keys (OpenAI, Anthropic, AWS), passwords, tokens and database connection strings belong in a .env file that is listed in .gitignore, loaded at runtime (for example with python-dotenv). Commit a .env.example with the variable names and fake values so others know what to set.

    
If you push a secret, treat it as stolen. Bots scan public GitHub for keys within minutes. Revoke or rotate the key first, at the provider. Deleting the file in a new commit does not help: the key is still in the history. Then tell your trainer.


    
Habits that prevent pain

    
    
      
  • Pull before you start, and before you push. Fewer surprises, fewer conflicts.
    • 
      
  • Run git status before git add . and before committing.
    • 
      
  • Never work on main; create a branch first.
    • 
      
  • Push at the end of every day. Your laptop can die; GitHub is your backup.
    • 
      
  • Don't commit generated files: outputs, caches, models, large data.
    • 
      
  • Read Git's messages. They usually tell you exactly what to do next ("use git pull…").
    • 
      
  • Don't panic and don't delete the folder. Almost every mistake is recoverable; ask before using --hard or --force.
    •
