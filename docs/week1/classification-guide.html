Classification: from logistic regression to boosting

A practical guide to the main classification algorithms, how to measure them properly, how to tune them, and how to tell whether a model is overfitting or underfitting, and why.

1Classification basics

Intuition. Classification answers "which group does this belong to?": spam or not, fraud or not, will churn or won't. Regression answers "how much?".

Binary vs multi-class

TypeNumber of classesExamples
Binary2 (usually coded 0 / 1)Spam / not spam · fraud / genuine · disease / healthy · churn / stay
Multi-class3 or more, one label eachDigit 0–9 · news topic · iris species
Multi-labelSeveral labels at onceA film tagged both "comedy" and "romance"

In binary classification, class 1 is the "positive" class: the thing you're looking for, usually the rarer and more important one (the fraud, the disease). "Positive" doesn't mean "good".

Probabilities and the threshold

Most classifiers don't output a hard yes/no. They output a probability (for example, 0.83 chance of fraud), which is turned into a class with a threshold:

Features
amount, time, country…
→
Model
→
Probability
0.83
→
Threshold 0.5
0.83 ≥ 0.5
→
Class 1
fraud

The default threshold is 0.5, but it's a business decision. Lowering it catches more positives at the cost of more false alarms (see Metrics).

The workflow

  1. Frame the problem: what is the positive class, and what does each kind of mistake cost?
  2. Explore and clean: missing values, outliers, duplicates, the class balance.
  3. Split into train and test data (stratified, so both keep the same class ratio) before any fitting.
  4. Preprocess inside a pipeline: imputation, encoding, scaling.
  5. Train several models and compare them with cross-validation.
  6. Tune the hyperparameters of the best ones.
  7. Evaluate once on the test set with the right metric, and choose the threshold.

2Logistic regression

Intuition. Add up the evidence (a weighted sum of the features), then squash it into a probability between 0 and 1 with the S-shaped sigmoid curve.

How it works

  1. Compute a score: z = b + w₁x₁ + w₂x₂ + … + wₙxₙ. This is exactly linear regression.
  2. Turn it into a probability: p = sigmoid(z) = 1 / (1 + e−z).
  3. Predict class 1 if p ≥ threshold.

Training finds the weights w that make the predicted probabilities match the real labels as closely as possible, by minimising log loss (cross-entropy). Log loss punishes confident wrong answers heavily.

Despite its name, logistic regression is a classification algorithm. "Regression" refers to the linear score inside it.

Try it: the sigmoid
Predict whether a student passes from the hours they studied. Change the weight, bias and threshold.

Reading the coefficients

Each weight shows how a feature pushes the prediction: positive pushes towards class 1, negative towards class 0. ew is the odds ratio: with w = 0.7 for "number of support calls", each extra call multiplies the odds of churning by e0.7 ≈ 2. Scale your features first if you want to compare weights with each other.

Strengths

  • Fast, simple, a strong baseline
  • Interpretable coefficients
  • Well-calibrated probabilities
  • Regularisation built in

Weaknesses

  • Linear decision boundary: underfits curved patterns unless you engineer features
  • Sensitive to outliers and to features on different scales
  • Correlated features make the weights unstable
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression

model = make_pipeline(StandardScaler(), LogisticRegression(C=1.0, max_iter=1000))
model.fit(X_train, y_train)
proba = model.predict_proba(X_test)[:, 1]   # probability of class 1

3Naive Bayes

Intuition. "Given what I see, which class is most likely?" Combine how common each class is with how typical each feature value is for that class, and pretend every feature is independent of the others (that's the "naive" part).

Bayes' theorem

P(class | features) ∝ P(class) × P(feature₁ | class) × P(feature₂ | class) × …

  • P(class), the prior: how common the class is overall (40% of emails are spam).
  • P(feature | class), the likelihood: how often the word "free" appears in spam vs normal email.
  • Multiply them for each class and predict the class with the highest result.

Worked example: an email contains "free" and "winner".

  • Spam: 0.4 (prior) × 0.30 ("free" in spam) × 0.20 ("winner" in spam) = 0.024
  • Not spam: 0.6 × 0.02 × 0.01 = 0.00012

Spam wins by a factor of about 200, so the email is classified as spam.

The independence assumption is almost never true ("free" and "winner" tend to appear together), yet Naive Bayes often works well anyway. Its probabilities tend to be over-confident, though, even when its rankings are good.

Variants

VariantFeature typeTypical use
GaussianNBContinuous numbers (assumes a bell curve per class)Sensor readings, measurements
MultinomialNBCountsText: word counts, TF-IDF
BernoulliNBBinary yes/noText: word present or absent
ComplementNBCounts, imbalanced classesImbalanced text classification

Smoothing: if a word never appeared in spam during training, its probability would be 0 and would wipe out everything else in the multiplication. Laplace smoothing (alpha) adds a small count to every feature so nothing is ever exactly zero.

Strengths

  • Extremely fast to train and predict
  • Works with little data
  • Great baseline for text
  • Handles many features

Weaknesses

  • The independence assumption is rarely true
  • Poorly calibrated probabilities
  • Usually beaten by trees and ensembles on tabular data

GaussianNB().fit(X_train, y_train)                 # numeric features
MultinomialNB(alpha=1.0).fit(X_counts, y_train)    # word counts

4Support vector machines (SVM)

Intuition. Draw the boundary between the classes that leaves the widest possible street on either side. Only the points on the edge of the street, the support vectors, decide where it goes.

Soft margin and C

Real data overlaps, so SVM allows some points inside the street, or even on the wrong side, with a penalty. C sets how much each violation costs:

  • Small C: a wide street that tolerates mistakes. Simpler and smoother, but can underfit.
  • Large C: a narrow street that tries to classify every training point correctly. Can overfit.

Kernels: curved boundaries

When no straight line separates the classes, the kernel trick implicitly maps the data into a higher-dimensional space where a straight line (a hyperplane) does separate them. Back in the original space, that boundary looks curved.

KernelBoundaryWhen
linearStraight line / planeMany features (e.g. text), or a roughly linear problem; fastest
rbf (default)Flexible, curved "blobs"A good general-purpose default
polyPolynomial curves of degree degreeKnown polynomial interactions

gamma (RBF and poly kernels) controls how far each training point's influence reaches. Low gamma: far-reaching influence and smooth boundaries. High gamma: only nearby points matter, giving wiggly boundaries that wrap around individual points, which means overfitting.

Always scale features for SVM. It is distance-based, so a feature measured in thousands would dominate one measured in single digits.

Strengths

  • Powerful with clear margins
  • Works in high dimensions (text)
  • Flexible through kernels
  • Uses only the support vectors, so it is memory-efficient

Weaknesses

  • Slow on large datasets (over about 50k rows)
  • Needs scaling and careful tuning of C and gamma
  • No native probabilities (probability=True is slower)
  • Hard to interpret
from sklearn.svm import SVC

model = make_pipeline(StandardScaler(), SVC(kernel="rbf", C=1.0, gamma="scale", probability=True))

5Decision trees

Intuition. A flowchart of yes/no questions, like the game "20 questions". Each question splits the data so the groups that result are as pure as possible, meaning mostly one class.

Vocabulary: the root node asks the first question, internal nodes ask further questions, branches are the answers, and the leaves give the prediction: the majority class, and the class proportions give the probability. Depth is the number of questions from the root to the deepest leaf.

How a split is chosen: Gini and entropy

At each node the tree tries every feature and every threshold, and keeps the split that makes the child groups purest.

Gini impurity

Gini = 1 − Σ pᵢ²

0 = perfectly pure. 0.5 = a 50/50 mix (the worst case with 2 classes). The default in scikit-learn; slightly faster.

Entropy

Entropy = −Σ pᵢ log₂ pᵢ

0 = pure. 1 = a 50/50 mix. "Information gain" is the drop in entropy after a split. In practice it gives very similar trees to Gini.

Worked example: a node has 10 customers: 5 churn, 5 stay. Gini = 1 − (0.5² + 0.5²) = 0.50.

Split on "month-to-month?" → left: 4 churn, 1 stay (Gini = 1 − (0.8² + 0.2²) = 0.32) · right: 1 churn, 4 stay (Gini = 0.32).

Weighted Gini after the split = 0.5 × 0.32 + 0.5 × 0.32 = 0.32. Impurity dropped from 0.50 to 0.32, so this is a good split.

Trees overfit easily

Left alone, a tree keeps splitting until every leaf is pure, which can mean one leaf per training example. That gives 100% training accuracy and a model that has memorised noise. Control it by:

  • Pre-pruning (stop early): max_depth, min_samples_split, min_samples_leaf, max_leaf_nodes
  • Post-pruning (grow it, then cut back): cost-complexity pruning with ccp_alpha
  • Ensembles: averaging many trees (next section)

Strengths

  • Very interpretable: you can draw it
  • No scaling needed
  • Handles non-linear patterns and interactions
  • Works with mixed feature types

Weaknesses

  • Overfits easily (high variance)
  • Unstable: a small change in the data can give a very different tree
  • Boundaries are step-shaped, parallel to the axes
  • Biased towards features with many split points
from sklearn.tree import DecisionTreeClassifier, plot_tree

tree = DecisionTreeClassifier(max_depth=4, min_samples_leaf=20, random_state=42).fit(X_train, y_train)
plot_tree(tree, feature_names=X_train.columns, class_names=["stay", "churn"], filled=True)

6Ensembles: bagging & boosting

Intuition. The "wisdom of crowds": many imperfect models combined are better than one. Bagging = many independent experts vote. Boosting = a team where each new member fixes the previous members' mistakes.

Base modelsStrong, deep trees (low bias, high variance)Weak, shallow trees (high bias, low variance)

Mainly reducesVariance (overfitting)Bias (underfitting)

Each bootstrap sample leaves out about 37% of the rows. These out-of-bag (OOB) rows give a free validation score (oob_score=True).

Why accuracy misleads on imbalanced data

Suppose 1% of transactions are fraud. A "model" that always predicts "not fraud" is 99% accurate and catches zero fraud. Accuracy is dominated by the majority class, so it rewards a model for ignoring the class you actually care about.

Rule: accuracy only makes sense when the classes are roughly balanced and both kinds of mistake cost about the same. Otherwise, use precision, recall, F1 and ROC-AUC / PR-AUC.

Try it: threshold, imbalance and model quality
1,000 cases. The model gives every case a score; cases at or above the threshold are predicted positive. Try 1–2% positives: compare the model's accuracy with "always predict 0", then raise the threshold and watch accuracy climb while recall collapses.

When to use precision, recall or F1

It depends on which mistake costs more:

Focus onWhenExamples
RecallMissing a positive (FN) is costly; false alarms are cheap to checkCancer screening · fraud detection · safety defects · security threats · churn (a retention call is cheap, losing the customer isn't)
PrecisionA false alarm (FP) is costly; missing some positives is acceptableSpam filter (losing a real email hurts) · blocking a customer's card · recommending a product · flagging content for removal · expensive interventions with a limited budget
F1Both matter, classes are imbalanced, and you want one number to compare modelsGeneral model comparison on imbalanced data
F-betaBoth matter but not equally: β > 1 weights recall more; β < 1 weights precision moreF2 for screening; F0.5 for spam
ROC-AUCComparing models' ranking ability regardless of thresholdChoosing the best model before setting a threshold
PR-AUC (average precision)Heavy imbalance (positives under about 5%)Fraud, rare disease, anomalies
AccuracyBalanced classes and equal costs onlyDigit recognition on a balanced dataset

Precision and recall trade off through the threshold. Lower the threshold and you flag more cases, so recall goes up and precision goes down. Raise it and the opposite happens. Choose the model with ROC-AUC or PR-AUC, then choose the threshold to fit the business cost of each mistake.

ROC-AUC and PR-AUC

  • ROC curve: recall (true positive rate) against false positive rate, at every threshold. The diagonal is random guessing.
  • AUC (area under the ROC curve): the probability that the model ranks a random positive above a random negative. 1.0 = perfect, 0.5 = random. It doesn't depend on the threshold or the class ratio, which makes it great for comparing models.
  • PR curve: precision against recall at every threshold. With very rare positives, ROC can look optimistic because the false positive rate stays tiny when there are huge numbers of negatives. The PR curve focuses on the positive class, so prefer PR-AUC / average precision under heavy imbalance. A random model's PR-AUC equals the positive rate, not 0.5.
from sklearn.metrics import classification_report, roc_auc_score, average_precision_score

print(classification_report(y_test, model.predict(X_test)))   # precision, recall, F1 per class
proba = model.predict_proba(X_test)[:, 1]
print("ROC-AUC:", roc_auc_score(y_test, proba))
print("PR-AUC: ", average_precision_score(y_test, proba))

8Hyperparameters

Intuition. Parameters are learned from the data (logistic regression weights, tree split points). Hyperparameters are settings you choose before training (tree depth, C, learning rate). They mostly control model complexity, and so the balance between underfitting and overfitting.

Tuning them: grid search vs random search

Grid search

Tries every combination in a grid. Thorough, but the cost multiplies quickly: 4 × 4 × 4 values × 5 folds = 320 fits. Good for 2–3 hyperparameters.

Random search

Tries N random combinations from ranges or distributions. Usually finds a good result much faster, because only a few hyperparameters really matter. Good for boosting models.

from sklearn.model_selection import GridSearchCV, RandomizedSearchCV, StratifiedKFold
from scipy.stats import randint, uniform

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)

grid = GridSearchCV(
    RandomForestClassifier(random_state=42, n_jobs=-1),
    param_grid={"max_depth": [4, 8, 12, None], "min_samples_leaf": [1, 5, 20]},
    scoring="f1", cv=cv,               # choose the metric that matches the business problem
).fit(X_train, y_train)
print(grid.best_params_, grid.best_score_)

search = RandomizedSearchCV(
    XGBClassifier(),
    param_distributions={
        "n_estimators": randint(100, 800), "learning_rate": uniform(0.01, 0.2),
        "max_depth": randint(2, 8), "subsample": uniform(0.6, 0.4), "colsample_bytree": uniform(0.6, 0.4),
    },
    n_iter=40, scoring="roc_auc", cv=cv, random_state=42,
).fit(X_train, y_train)

Choose the tuning metric deliberately. The default scoring is accuracy, which is the wrong target for imbalanced data. Use "f1", "recall", "roc_auc" or "average_precision".

9Cross-validation

Intuition. One train/test split is one roll of the dice: you might get a lucky or unlucky test set. Cross-validation repeats the split several times and averages the scores, giving a more reliable estimate and showing how much it varies.

Why not just one train/test split?

  • The score depends on which rows ended up in the test set, so it's noisy, especially with small data.
  • If you tune hyperparameters against the test set, you slowly overfit to the test set, and it no longer measures real-world performance.

So split three ways: train (fit) · validation (choose models and hyperparameters) · test (a final, one-time check). Cross-validation recycles the training data to act as the validation set.

K-fold cross-validation

Try it: K-fold
The training data is split into K folds. Each round trains on K−1 folds (blue) and validates on the remaining one (orange). The final score is the average of K scores.

VariantUse whenscikit-learn
K-foldRegression, or balanced classificationKFold(n_splits=5, shuffle=True)
Stratified K-foldClassification: keeps the class ratio the same in every fold (essential when classes are imbalanced)StratifiedKFold(n_splits=5, shuffle=True)
Time-series splitTime-ordered data: always train on the past and validate on the future, never shuffleTimeSeriesSplit(n_splits=5)
Group K-foldSeveral rows per customer or patient: keep each group within a single fold to avoid leakageGroupKFold(n_splits=5)
Leave-one-outTiny datasets (K = number of rows); expensiveLeaveOneOut()

Choosing K: 5 or 10 is standard. Larger K = more training data per round (less pessimistic) but more fits and more time.

from sklearn.model_selection import cross_val_score, cross_validate, StratifiedKFold
from sklearn.pipeline import make_pipeline

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
pipe = make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000))

scores = cross_val_score(pipe, X_train, y_train, cv=cv, scoring="f1")
print(f"F1: {scores.mean():.3f} ± {scores.std():.3f}")

# Train AND validation scores, to diagnose over/underfitting
res = cross_validate(pipe, X_train, y_train, cv=cv, scoring="f1", return_train_score=True)
print("train", res["train_score"].mean(), "validation", res["test_score"].mean())

Avoid leakage: put scaling, imputation, encoding and resampling (SMOTE) inside a pipeline, so they're fitted on each training fold only. If you scale the whole dataset before cross-validation, information from the validation fold leaks into training and the scores come out too optimistic.

A high standard deviation across folds (for example F1 0.70 ± 0.15) means the model is unstable or the data is small. That's often a sign of overfitting.

10Overfitting vs underfitting

Underfitting (high bias)

The model is too simple to capture the pattern. It does badly on training data and on new data. Like a student who didn't study: wrong on both the practice and the real exam.

Overfitting (high variance)

The model memorised the training data, noise included. Excellent on training data, much worse on new data. Like a student who memorised the practice answers but can't handle new questions.

Try it: model complexity
For example a decision tree's max_depth, or SVM's C. Training error keeps falling as complexity grows; validation error falls and then rises again.

Why it happens

Causes of underfittingCauses of overfitting
Model level
  • The model is too simple for the pattern (a linear model on curved data)
  • Too much regularisation: small C, large alpha, large min_samples_leaf
  • Trees too shallow (max_depth 1–2)
  • Too few boosting rounds, or too low a learning rate
  • Training stopped early (max_iter too low, no convergence)
  • The algorithm's assumptions don't fit the data (Naive Bayes when features strongly interact)
  • The model is too complex: deep or unpruned trees, a high polynomial degree
  • Too little regularisation: large C, high gamma, ccp_alpha = 0
  • Too many boosting rounds, or too high a learning rate, without early stopping
  • Too many hyperparameters tuned on one small validation set
  • A small k in KNN (k = 1 memorises)
Data level
  • Missing important features: the inputs don't contain the signal
  • Poor feature engineering (no interactions, no ratios, raw dates)
  • Features not scaled for SVM, KNN or logistic regression
  • Categories badly encoded (arbitrary numbers for non-ordered categories)
  • Very noisy features or labels that hide the pattern
  • Heavy class imbalance pushing the model to always predict the majority
  • Too little training data for the model's complexity
  • Too many features compared with rows (high dimensionality), including irrelevant ones
  • Noisy labels or outliers that the model memorises
  • Duplicates or near-duplicates across train and test
  • A training set that isn't representative of real data
  • Oversampling (SMOTE) before splitting, so copies of training points end up in validation

Data leakage looks like a great fit, not overfitting: validation scores are suspiciously high because the model saw information it won't have in real life (a feature recorded after the outcome, scaling fitted on all the data, duplicates across the split). Then it fails in production. If results look too good to be true, check for leakage.

How to fix it

Fixing underfitting

  • Use a more flexible model (trees, ensembles, an RBF SVM)
  • Reduce regularisation (raise C, lower alpha)
  • Allow deeper trees or more boosting rounds
  • Engineer better features: interactions, ratios, domain knowledge
  • Scale and encode correctly
  • Handle imbalance (class weights, SMOTE, threshold)
  • Train longer (max_iter)

Fixing overfitting

  • Get more training data
  • Simplify the model: limit max_depth, raise min_samples_leaf, prune
  • Add regularisation (lower C, raise reg_lambda)
  • Remove irrelevant features (feature selection, L1)
  • Use bagging or random forests to average out variance
  • Early stopping for boosting; subsample rows and columns
  • Clean noisy labels and outliers; deduplicate
  • Validate with cross-validation, not a single split
