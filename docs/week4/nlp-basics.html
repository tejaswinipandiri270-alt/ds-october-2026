Week 4 · NLP, Transformers & LLMs

NLP basics: from raw text to embeddings

Models only understand numbers. This guide follows one question from start to finish: how do we turn a restaurant review into numbers a model can use? We clean and split text, count words, learn word embeddings, let context change meaning with transformers, and finish with sentence embeddings and semantic search, the retrieval step behind RAG.

Companion notebook: 01_nlp_vectorization_restaurant_reviews.ipynb. Every number quoted on this page comes from that notebook.

1What is NLP?

Intuition. Natural language processing (NLP) is the craft of turning messy human language into numbers that keep as much of its meaning as possible, so that a model can classify, search, summarise or generate it.

NLP covers any task where the input or output is human language. Some everyday examples:

TaskInput → outputExample
Text classificationtext → labelIs this review positive or negative? Is this email spam?
Named entity recognitiontext → tagged spansFind the people, places and dates in a contract
Semantic search / retrievalquestion → most relevant documentsFind reviews that complain about slow service
Summarisationlong text → short textSummarise 200 reviews for the restaurant owner
Translationtext in one language → anotherEnglish → French menu
Question answering / chatquestion (+ documents) → answerAn assistant that answers using company policies (RAG)

Whatever the task, the first job is always the same: represent text as numbers. This page walks through the main ways of doing that, in roughly the order they were invented:

3Tokenisation: splitting text into pieces

Intuition. Before you can count or embed anything, you must decide what "a piece of text" is. That piece is a token.

A token is the unit a model works with: usually a word, sometimes punctuation, sometimes part of a word. Three levels you'll meet:

Level"Wasn't unbelievable!" becomesUsed by
str.split() (whitespace)["Wasn't", "unbelievable!"]Quick hacks only: punctuation stays glued on
Word tokeniser (nltk.word_tokenize)["Was", "n't", "unbelievable", "!"]Classic NLP: BoW, TF-IDF, Word2Vec
Sub-word tokeniser (WordPiece, BPE)Rare words split into known pieces, e.g. unbelievably → un ##bel ##ie ##va ##bly (BERT, section 14)BERT, GPT and every modern LLM

From the notebook, with NLTK's real tokeniser:

review = "Wow... Loved this place! The wasn't-so-great service didn't ruin it :)"
review.split()
# ['Wow...', 'Loved', 'this', 'place!', 'The', "wasn't-so-great", 'service', "didn't", 'ruin', 'it', ':)']
word_tokenize(review)
# ['Wow', '...', 'Loved', 'this', 'place', '!', 'The', "wasn't-so-great", 'service', 'did', "n't", 'ruin', 'it', ':', ')']
  • str.split() gives you place! and place as two different words.
  • word_tokenize separates punctuation and splits contractions: didn't → did + n't. That matters for sentiment, as you'll see in section 5.
  • Sub-word tokenisers break rare words into known pieces, so an LLM never meets an "unknown word". Section 14 shows BERT's real output.

4Normalisation

Intuition. "Food", "FOOD" and "food!!!" mean the same thing. Normalisation makes them look the same so they're counted once.

def normalise(text: str) -> str:
    text = text.lower()
    text = re.sub(r"http\S+", " ", text)      # URLs
    text = re.sub(r"[^a-z'\s]", " ", text)    # keep letters and apostrophes
    return re.sub(r"\s+", " ", text).strip()

normalise("The FOOD was AMAZING!!! 10/10, see http://example.com")
# 'the food was amazing see'

Typical normalisation steps, and when to be careful:

StepWhyWatch out
Lower-casing"Great" = "great"Loses SHOUTING (a sentiment signal) and names ("Apple" the company)
Remove URLs, emails, HTMLNoise for most tasksSometimes the domain is useful (spam detection)
Remove numbers"10/10" rarely generalises"0 stars" vs "5 stars", prices, dosages
Remove punctuation"place!" = "place""!!!" and ":)" carry emotion; we keep apostrophes for "n't"
Collapse whitespaceTidy tokensNothing, always safe

Only for classic models. Transformers (BERT, sentence embeddings, LLMs) have their own tokenisers and learned from raw text, so you pass them the original review. Cleaning can even hurt them. In the notebook, the 0.903 sentence-embedding score used raw reviews.

5Stop words, and the negation trap

Intuition. Very common words like the, is, and appear in every review, so they don't help tell reviews apart. Removing them shrinks the vocabulary. But one family of "common words" decides the whole meaning.

NLTK's English list has 198 stop words. It includes no, nor, not and 18 contractions such as don't, wasn't, isn't.

text = "the food was not good and the service wasn't great"
Remove all stop words:  ['food', 'good', 'service', 'great']               # a complaint became praise!
Keep negations:         ['food', 'not', 'good', 'service', 'not', 'great']

The trap: removing every stop word turns "the food was not good" into "food good". For sentiment analysis, keep the negations.

A second, subtler trap: word_tokenize splits wasn't into was + n't, so the stop list entry "wasn't" never matches anything. The notebook fixes this by mapping every n't token to not:

NEGATIONS = {"not", "no", "nor"} | {w for w in STOP if w.endswith("n't")}
STOP_KEEP_NEG = STOP - NEGATIONS

def tokenise(text: str) -> list[str]:
    return ["not" if t == "n't" else t for t in word_tokenize(text)]   # wasn't → was + not

Did it matter? Yes. Same model, same folds, only the stop list changed:

RepresentationCV accuracy
Bag of Words, stop words including "not" removed0.786
Bag of Words, negations kept0.815

And when the trained TF-IDF model's weights were inspected, the single most negative word was not, followed by bad, no, never, terrible, slow.

6Stemming vs lemmatisation (and POS tags)

Intuition. "loved", "loving" and "loves" are the same idea. Reducing them to one base form means the model sees one strong signal instead of three weak ones.

Stemming

  • Chops endings off with fixed rules (Porter stemmer)
  • Very fast, no dictionary
  • Can produce non-words: studies → studi, was → wa

Lemmatisation

  • Looks the word up in a dictionary (WordNet)
  • Needs the part of speech to work well
  • Always returns a real word: studies → study, was → be

Part-of-speech (POS) tagging

A POS tagger labels each token as a noun, verb, adjective, adverb and so on (nltk.pos_tag). Without a tag, WordNet assumes every word is a noun, which is why loved stayed loved and was became the odd wa.

Tagging is a guess. On a lone word it has no context: here better was tagged as an adverb, so it became well (as an adjective it would have been good). Inside real sentences the tagger does much better, which is why the notebook tags whole reviews, not single words.

The full cleaning pipeline used for the classic models:

def clean(text, keep_negations=True, lemmatise=True):
    tokens = tokenise(normalise(text))
    stop = STOP_KEEP_NEG if keep_negations else STOP
    tokens = [t for t in tokens if t not in stop and len(t) > 1]
    if lemmatise:
        tokens = [lemmatizer.lemmatize(t, wordnet_pos(tag)) for t, tag in nltk.pos_tag(tokens)]
    return " ".join(tokens)

"Crust is not good."   →  "crust not good"

7n-grams: keeping a little word order

Intuition. Single words forget their neighbours. "not good" as one feature is far more informative than "not" and "good" separately.

An n-gram is a run of n tokens in a row: unigrams (1), bigrams (2), trigrams (3).

tokens:  ['crust', 'not', 'good']
bigrams: [('crust', 'not'), ('not', 'good')]
  • In scikit-learn: CountVectorizer(ngram_range=(1, 2)) keeps unigrams and bigrams.
  • On the reviews, adding bigrams moved BoW from 0.815 to 0.818 and TF-IDF from 0.821 to 0.829.
  • The cost: the vocabulary grows quickly (every pair of neighbours is a new column), so the matrix gets even sparser.

8One-hot encoding and Bag of Words

Intuition. Make a list of every word you've ever seen. Describe each review by ticking (or counting) which words it uses. Throw word order away: it's a "bag" of words.

One-hot vectors

With a vocabulary of V words, each word is a vector of length V with a single 1. With the vocabulary [food, good, not, service, the, was], "good" is [0, 1, 0, 0, 0, 0]. Every pair of different words is equally far apart, so one-hot vectors carry no meaning: "tasty" is as different from "delicious" as from "laptop".

Bag of Words (BoW)

Add up the one-hot vectors of a review's words and you get its count vector. The notebook's mini example:

foodgoodnotservicethewas
the food was good110011
the food was not good111011
good service good food120100

"The food was good" and "the food was not good" mean opposite things, yet their vectors differ in a single column. Their cosine similarity is 0.89. Bigrams help: adding not good as its own column separates them further.

from sklearn.feature_extraction.text import CountVectorizer
bow = CountVectorizer()                      # or CountVectorizer(ngram_range=(1, 2))
X = bow.fit_transform(texts)                 # sparse matrix: rows = reviews, columns = vocabulary
bow.get_feature_names_out()                  # the vocabulary

Fit on training data only. The vocabulary (and, for TF-IDF, the IDF weights) are learned from the data. Fitting on the test set leaks information. Put the vectoriser inside a Pipeline so cross-validation refits it per fold, as the notebook does.

9TF-IDF: weighting words by how informative they are

Intuition. A word that appears in every review ("food", "place") tells you little. A word that appears in only a few ("rude", "wow") is a strong clue. TF-IDF turns that idea into a weight.

tf-idf(word, review) = tf(word, review) × idf(word)

tf = how many times the word appears in this review
idf = log( N / df )   N = number of reviews, df = reviews containing the word

scikit-learn's TfidfVectorizer uses a slightly smoothed version, then scales each review vector to length 1 (L2 normalisation), so long and short reviews are comparable:

idf = ln( (1 + N) / (1 + df) ) + 1 then v = v / ‖v‖

Worked example (the same three sentences)

N = 3. "food" and "good" appear in all 3 sentences, "the" and "was" in 2, "not" and "service" in 1:

Worddfidf = ln(4 / (1+df)) + 1Meaning
food, good3ln(4/4) + 1 = 1.000everywhere → lowest weight
the, was2ln(4/3) + 1 = 1.288common
not, service1ln(4/2) + 1 = 1.693rare → highest weight

For "the food was not good": raw weights are food 1, good 1, not 1.693, the 1.288, was 1.288. The vector length is √(1 + 1 + 1.693² + 1.288² + 1.288²) = 2.861. Dividing by it gives:

10Sparsity, and the limits of counting

On the full data the BoW matrix is 1,000 reviews × 1,662 words, but only 5,654 of 1,662,000 cells are non-zero: 0.34%. Each review uses a handful of words, so the vectors are almost all zeros. This is a sparse representation, and scikit-learn stores only the non-zero entries.

Strengths of BoW / TF-IDF

  • Fast, cheap, no GPU, no downloads
  • Explainable: one weight per word
  • Strong baseline on short, domain-specific text
  • Great for keyword search (BM25 is a TF-IDF cousin)

Limits

  • No meaning: "delicious" and "tasty" are unrelated columns
  • Huge and sparse: one column per word (or bigram)
  • No context: "cold beer" (good) and "cold food" (bad) share one cold column
  • Unknown words: a word not seen in training is ignored

Every method from here on tries to fix those limits by learning the numbers instead of counting them.

11Word2Vec: learning word meaning from neighbours

Intuition. "You shall know a word by the company it keeps" (J. R. Firth). If "pasta" and "risotto" keep appearing next to the same words ("delicious", "ordered", "plate"), they probably mean similar things, so give them similar vectors.

An embedding represents each word as a short, dense list of numbers (say 50 or 300), all non-zero. Word2Vec (Google, 2013) learns them with a tiny neural network trained on a guessing game over a sliding window of neighbouring words.

CBOW (Continuous Bag of Words)Skip-gram
TaskPredict the middle word from its neighboursPredict the neighbours from the middle word
Examplethe ___ was delicious → pastapasta → the, was, delicious
StrengthsFaster; smooths over frequent wordsBetter for rare words and small data
gensimsg=0sg=1

The network has one hidden layer with no activation. After training, the guessing game is thrown away and the weights of the hidden layer are the embeddings: row i is the vector for word i.

Negative sampling keeps training cheap. Instead of scoring every word in the vocabulary at each step (a huge softmax), the model learns to say "yes" to the real neighbour and "no" to a few random words (the negatives), e.g. 5–20 per real pair.

from gensim.models import Word2Vec
sentences = [t.split() for t in df["clean"]]
cbow     = Word2Vec(sentences, vector_size=50, window=3, min_count=2, sg=0, epochs=200, seed=42, workers=1)
skipgram = Word2Vec(sentences, vector_size=50, window=3, min_count=2, sg=1, epochs=200, seed=42, workers=1)
cbow.wv["food"][:8]           # [-0.77 -1.01  0.62  1.37  0.33 -0.25  0.25  0.04]
cbow.wv.most_similar("great") # ['provide', 'hip', 'impeccable', 'perfection', 'watch', 'delish']

Small data, noisy vectors. 1,000 short reviews are only about 10,000 words. Neighbours of "great" such as provide and watch are noise. Word2Vec needs millions of sentences, which is why we usually reuse embeddings pretrained on huge corpora.

Key parameters: vector_size (dimensions), window (how many neighbours each side), min_count (ignore rarer words), sg (0 CBOW, 1 skip-gram), negative (negative samples), epochs.

12GloVe: pretrained word vectors

Intuition. Rather than sliding a window and guessing, GloVe counts how often every pair of words appears together across a giant corpus, then finds vectors whose dot products reproduce those co-occurrence statistics.

GloVe (Global Vectors, Stanford, 2014). The notebook loads glove-wiki-gigaword-50: 400,000 words, 50 dimensions, trained on Wikipedia and newswire (about 66 MB, downloaded once).

import gensim.downloader as api
glove = api.load("glove-wiki-gigaword-50")

glove.most_similar("delicious")   # tasty, savory, spicy, dessert, flavorful, flavor
glove.most_similar("waiter")      # waitress, bartender, hairdresser, doorman, waiters, busboy
glove.most_similar(positive=["king", "woman"], negative=["man"])   # queen
PairCosine similarityReading
delicious, tasty0.93near-synonyms
waiter, waitress0.88same role
delicious, disgusting0.51opposites, yet fairly close
food, laptop0.32unrelated

Similar contexts ≠ same meaning. "Delicious" and "disgusting" both appear around food, so their vectors are fairly close. Embeddings capture what a word is used for, not whether it's good or bad. That is a real limitation for sentiment.

From word vectors to a review vector

A classifier needs one vector per review. The simplest approach: average the word vectors.

def avg_glove(text):
    vecs = [glove[w] for w in text.split() if w in glove]
    return np.mean(vecs, axis=0) if vecs else np.zeros(glove.vector_size)
# 1000 × 50 matrix → logistic regression → accuracy 0.765

Only 50 dense numbers that "know" tasty ≈ delicious, yet it scored below plain Bag of Words. Averaging blurs everything: word order and negation vanish ("not good" ≈ "good"), and the vectors were trained on news, not reviews. Static embeddings alone are not an automatic upgrade.

FastText (Facebook) is a Word2Vec variant that also learns vectors for character n-grams, so it can build a vector for a misspelt or unseen word like "honeslty".

14Context matters: attention, transformers and BERT

Intuition. A static embedding gives "cold" one vector, whatever the sentence. But "cold" is a compliment in "an ice cold beer" and a complaint in "the food arrived cold". The fix is to let every word look at its neighbours before deciding what it means.

Attention, in plain words

Attention lets each word score every other word in the sentence for relevance, then rebuild its own vector as a weighted mix of them. In "the food arrived cold", cold pays most attention to food and arrived; in "ice cold beer", to ice and beer. So the output vector for cold differs between the two sentences.

Mechanically, each token's vector is projected into a query, a key and a value. A token's query is compared (dot product) with every key; a softmax turns those scores into weights; the weights mix the values. Many such heads run in parallel, each free to track a different relationship.

Attention(Q, K, V) = softmax( Q·Kᵀ / √d ) · V

The transformer

A transformer (Google, 2017, "Attention Is All You Need") stacks many attention layers with small feed-forward networks between them. It reads the whole sentence at once, in parallel, unlike RNNs and LSTMs that read one word at a time. That parallelism is what made training on enormous amounts of text practical.

Encoder (reads)

Every token sees every other token, left and right. Produces contextual embeddings. Good for classification, search and extraction. BERT is an encoder.

Decoder (writes)

Each token only sees the tokens before it, and predicts the next one. Good for generating text. GPT, Llama and other chat LLMs are decoders.

BERT

BERT (Bidirectional Encoder Representations from Transformers, Google, 2018) was pretrained on books and Wikipedia with two games:

  1. Masked language modelling: hide 15% of the words and predict them using context from both sides.
  2. Next sentence prediction: does sentence B really follow sentence A?
fill = pipeline("fill-mask", model="bert-base-uncased")
fill("The food was absolutely [MASK], we will definitely come back.")
# delicious 0.208 · amazing 0.151 · wonderful 0.133 · fantastic 0.116 · fabulous 0.087

WordPiece sub-word tokens

BERT uses a vocabulary of about 30,000 WordPiece tokens. Common words are one token; rare words are split into pieces, with ## marking a continuation:

theti##ram##is##uwasun##bel##ie##va##blysc##rum##pt##ious!

That's "The tiramisu was unbelievably scrumptious!", from the notebook. BERT never meets an "unknown" word. GPT-style models use a similar idea called byte-pair encoding (BPE).

Special tokens: [CLS] and [SEP]

BERT adds [CLS] at the start of every input and [SEP] at the end (and between two sentences). The final vector of [CLS] is trained to summarise the whole input, so classification heads are put on top of it. [MASK] marks hidden words during pretraining and in the fill-mask demo.

15Sentence embeddings and cosine similarity

Intuition. We usually want one vector per review, not per word. Sentence-embedding models are trained so that two sentences with the same meaning land close together, even if they share no words.

Sentence-Transformers take a BERT-style encoder, pool (average) its token vectors into one, and fine-tune it on pairs of sentences that should be close (paraphrases, question and answer) or far apart. all-MiniLM-L6-v2 is small (6 layers), fast on a laptop CPU, and outputs 384 numbers per sentence.

from sentence_transformers import SentenceTransformer
st_model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
X_st = st_model.encode(df["Review"].tolist(), normalize_embeddings=True)   # raw reviews, no cleaning
X_st.shape                     # (1000, 384)
# logistic regression on these vectors → accuracy 0.903

Cosine similarity

To compare two embeddings we measure the angle between them, ignoring their length:

cos(a, b) = (a · b) / (‖a‖ × ‖b‖) 1 = same direction · 0 = unrelated · −1 = opposite

If vectors are normalised to length 1 (normalize_embeddings=True), cosine similarity is simply the dot product, which is why the notebook's search can use X_st @ q.

16Semantic search: the "R" in RAG

Intuition. Embed every document once. When a question arrives, embed it too, and return the documents whose vectors point in the most similar direction. You're searching by meaning, not by matching keywords.

def search(query, k=5):
    q = st_model.encode([query], normalize_embeddings=True)[0]
    scores = X_st @ q                          # cosine similarity (vectors are normalised)
    top = np.argsort(-scores)[:k]
    return df["Review"].iloc[top], scores[top]

What works: the top match for the staff complaint contains neither "slow" nor "ignored", yet it's exactly about that. Keyword search (BoW / TF-IDF) would have missed it.

What to notice: "The staff was very attentive" (praise) ranks second for a complaint, and "Not good for the money" tops "great value". Embeddings capture the topic much more strongly than the opinion.

For RAG that's fine: when the question is about service, you want reviews about service, and the LLM then reads them and judges the opinion. For sentiment classification you still put a classifier on top, as in the 0.903 result. At scale, the matrix product is replaced by a vector database (FAISS, OpenSearch, pgvector, Chroma) that finds nearest neighbours quickly among millions of vectors.

Lessons

  1. Preprocessing choices matter. Keeping negations was worth about 3 points (0.786 → 0.815), more than switching BoW to TF-IDF.
  2. Small gaps are noise. BoW, BoW + bigrams, TF-IDF and TF-IDF + bigrams are all within one standard deviation of each other. Don't crown a winner on a 0.003 difference.
  3. Dense isn't automatically better. Averaged GloVe (0.765) lost to plain word counts: averaging destroys order and negation, and the vectors came from a different domain.
  4. Context wins. Pretrained sentence embeddings came out clearly on top (0.903), on raw text, with no cleaning at all.
  5. Always keep a cheap baseline. TF-IDF + logistic regression trains in milliseconds, is explainable word by word, and got within about 7 points.

18From embeddings to LLMs, in brief

StageWhat happensDataResult
1. PretrainingPredict the next token, billions of timesTrillions of tokens: web, books, codeA base model that knows language and facts but only continues text

  • BERT is an encoder: it reads and produces embeddings. GPT-style LLMs are decoders: they write, one token at a time.
  • An LLM's context window is measured in tokens, and API pricing is per token, so tokenisation still matters.
  • RAG (retrieval-augmented generation) joins the two halves: an embedding model retrieves relevant documents (section 16), and an LLM writes an answer grounded in them. Notebook 2 and the prompt-engineering material build on this.

19Common pitfalls

PitfallWhat goes wrongFix
Removing negations as stop words"not good" becomes "good"; accuracy drops (0.815 → 0.786)Remove not, no, nor and n't forms from the stop list
Contractions split by the tokeniserwasn't → was + n't, so a stop list entry "wasn't" never matchesMap n't → not after tokenising
Fitting the vectoriser on all dataVocabulary and IDF leak test information; scores are optimisticPut the vectoriser in a Pipeline; fit on training folds only
Cleaning text for transformersLower-casing, stop-word removal and lemmatising strip signal BERT-style models usePass raw text to transformer models
Lemmatising without POS tagswas → wa, loved unchangedTag first; map tags to WordNet POS
Training Word2Vec on tiny dataNeighbours are noiseUse pretrained vectors (GloVe, FastText) or a sentence-embedding model
Trusting embedding similarity as sentiment"delicious" ≈ "disgusting" (0.51); praise retrieved for a complaintUse embeddings to find the topic; a classifier or LLM to judge the opinion
Comparing unnormalised vectors with a dot productLong documents win just for being longNormalise, or use cosine similarity
Over-reading tiny differencesPicking 0.821 over 0.818 when std is 0.02Report mean ± std across folds
Mixing embedding modelsQuery embedded with model A, documents with model B: similarities are meaninglessUse the same model (and version) for both

21Glossary

Token
The unit a model processes: a word, punctuation mark or sub-word piece.
Corpus
The collection of documents you work with (here, 1,000 reviews).
Vocabulary
The set of distinct tokens a vectoriser or model knows.
Normalisation
Making equivalent text look identical: lower-casing, removing URLs, numbers and punctuation.
Stop words
Very common words often removed before counting. Keep negations for sentiment.
Stemming
Rule-based chopping of word endings; fast but can produce non-words.
Lemmatisation
Dictionary lookup of a word's base form, guided by its part of speech.
POS tag
Part-of-speech label (noun, verb, adjective, adverb…) assigned to a token.
n-gram
A run of n consecutive tokens; bigrams keep some word order.
One-hot vector
A vocabulary-length vector with a single 1 for one word.
Bag of Words
A document as a vector of word counts, ignoring order.
TF-IDF
Term frequency × inverse document frequency: counts weighted so rare words matter more.
Sparse vector
Mostly zeros; only non-zero entries are stored.
Dense vector
A short vector where every entry carries information.
Embedding
A learned dense vector in which similar meanings lie close together.
Word2Vec
Learns word embeddings by predicting words from neighbours (CBOW) or neighbours from words (skip-gram).
Negative sampling
Training shortcut: contrast each real word pair with a few random "wrong" words.
GloVe
Pretrained word embeddings fitted to global co-occurrence counts.
Static embedding
One fixed vector per word, whatever the sentence.
Contextual embedding
A word vector that depends on the surrounding sentence (BERT).
Attention
Each token weighs every other token to rebuild its own vector from context.
Transformer
A network of stacked attention and feed-forward layers that processes all tokens in parallel.
Encoder / decoder
Encoders read in both directions and produce embeddings (BERT); decoders generate the next token (GPT).
BERT
A transformer encoder pretrained with masked language modelling.
WordPiece / BPE
Sub-word tokenisers that split rare words into known pieces.
[CLS]
BERT's special first token whose final vector summarises the input.
Sentence embedding
One vector for a whole sentence or passage, e.g. all-MiniLM-L6-v2 (384 dims).
Cosine similarity
The cosine of the angle between two vectors: 1 same direction, 0 unrelated.
Semantic search
Retrieving documents by embedding similarity rather than keyword overlap.
Vector database
A store that finds nearest-neighbour vectors quickly at scale (FAISS, OpenSearch, pgvector).
RAG
Retrieval-augmented generation: retrieve relevant documents, then have an LLM answer from them.
