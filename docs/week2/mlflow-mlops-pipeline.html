MLflow in practice and the MLOps pipeline

You have already trained, logged, tagged and compared models in MLflow. This page turns that into a repeatable system: consistent tags so runs are easy to find, a registry with a champion and a challenger, a fair promotion rule, and a pipeline that watches the live model, notices when the world has changed (drift), retrains and only swaps models when the new one has genuinely earned it.

1Recap: the MLflow vocabulary

Intuition. MLflow is a lab notebook that fills itself in. Every training attempt is written down with its settings, its scores and its outputs, so you can find it, compare it and reuse it later.

This page builds on the Week 2 introduction. If any word below is new, read MLflow & experiment tracking first: it covers installing MLflow, manual logging, autolog, logging figures and the basics of the registry.

TermWhat it isExample on this courseHow you log it
ExperimentA folder of runs that answer one questionchurn-week3mlflow.set_experiment("churn-week3")
RunOne training attempt, with an ID, a name, a start and an endrf-depth6with mlflow.start_run(run_name=...):
ParameterA setting you chose before training. Stored as textmax_depth = 6mlflow.log_param / log_params
MetricA number measured during or after training. Can have one value per step (epoch)test_f1 = 0.85mlflow.log_metric(..., step=epoch)
ArtifactAny file saved with the run: a model, a plot, a CSVconfusion_matrix.pngmlflow.log_artifact, log_figure
ModelA special artifact that MLflow knows how to load againThe fitted random forestmlflow.sklearn.log_model(model, name="model")
TagA free-text label (key = value) on a run or experiment, used to organise and filter. Can be changed after the runmodel_family = nnmlflow.set_tag / set_tags
Tracking storeWhere all of this is keptA local SQLite file, mlflow.dbmlflow.set_tracking_uri("sqlite:///mlflow.db")

Where your runs live. In MLflow 3 the default local store is a SQLite database called mlflow.db in the folder you run Python from. Every example on this page sets it explicitly with mlflow.set_tracking_uri("sqlite:///mlflow.db"), so the code, the UI and the registry all point at the same file. The examples were tested with MLflow 3.17.1.

2Tagging experiments and runs

Intuition. Tags are sticky labels. Parameters and metrics describe what the model did; tags describe what the run is: which family, which dataset, who ran it, and what role it plays.

Three levels of tags

LevelSet withUse it for
Experiment tagsmlflow.set_experiment_tags({...})Facts about the whole experiment: project, team, a description
Run tagsmlflow.start_run(tags={...}), mlflow.set_tag(k, v), mlflow.set_tags({...})Facts about one run: model family, algorithm, dataset version, author
Model version tagsMlflowClient().set_model_version_tag(...)Facts about a registered version (see section 5)

The description tag

MLflow treats one tag specially: mlflow.note.content. Whatever text you put there is shown as the description of the run (or of the experiment, if you set it as an experiment tag) in the UI. It accepts Markdown. Use it to say, in one or two sentences, why the run exists.

System tags: the ones MLflow adds for you

Tags whose names start with mlflow. are system tags. MLflow fills most of them in automatically. You can filter on them like any other tag.

System tagContains
mlflow.runNameThe run name you passed to start_run (or a random one such as bright-owl-42)
mlflow.userYour operating-system user name
mlflow.source.nameThe script or notebook that started the run
mlflow.source.typeWhere it ran: LOCAL, NOTEBOOK, JOB…
mlflow.source.git.commitThe Git commit of your code, added automatically when the script is inside a Git repository
mlflow.note.contentThe description (you set this one yourself)
mlflow.parentRunIdSet on child runs when you use nested runs

A tagging convention for the course

Tags only help if everyone uses the same keys and the same values. "NN", "nn" and "neural" are three different values to a filter. Agree a small set of keys as a team and write them down.

Tag keyAllowed valuesWhy
model_familyml · nnCompare classical models with neural networks, or find the best of each
algorithmlogistic_regression · random_forest · keras_dnn · mlpGroup runs of the same algorithm across different settings
stagebaseline · experimentSeparate the simple "bar to beat" from the attempts to beat it
dataset_versionchurn-v1, churn-v2, or a date such as 2026-06Only compare runs trained on the same data; trace a model back to its data
authorYour first nameWho to ask about a run (more readable than mlflow.user)
git_commitShort commit hashReproduce the exact code (MLflow adds mlflow.source.git.commit automatically when it can)
candidatechampion · challengerMark which runs are in contention for deployment

Tags are not aliases. A candidate = champion run tag is a note for humans. The thing that actually decides which model is served is the registry alias @champion (section 5). Keep them in step, but trust the alias.

Tagging in code

The examples on this page use a synthetic customer-churn dataset (made-up customers, a 0/1 "churned" target). Save this helper as common.py next to your scripts; the drift argument is used later to create "the world has changed" data.

# common.py
import numpy as np
import pandas as pd

def make_churn_data(n=4000, seed=0, drift=0.0):
    """Synthetic customer-churn data. drift=0 is the 'old' world; drift=1 is a fully changed world."""
    rng = np.random.default_rng(seed)
    df = pd.DataFrame({
        "tenure_months": rng.integers(1, 72, n).astype(float),
        "monthly_charges": rng.normal(60 + 25 * drift, 15, n).round(2),
        "support_calls": rng.poisson(1.5 + 1.5 * drift, n).astype(float),
        "age": rng.normal(45, 12, n).round(),
        "contract": rng.choice([0.0, 1.0, 2.0], n,            # 0 monthly, 1 one-year, 2 two-year
                               p=[0.5 + 0.2 * drift, 0.3 - 0.1 * drift, 0.2 - 0.1 * drift]),
    })
    # Concept drift: what drives churn changes as drift grows
    logit = 2 * (-0.3 - 0.5 * drift
             + (-0.05 + 0.06 * drift) * (df.tenure_months - 36)   # loyal customers start leaving
             + 0.03 * (df.monthly_charges - 60 - 25 * drift)
             + (0.6 - 0.6 * drift) * (df.support_calls - 1.5 - 1.5 * drift)
             + 1.0 * (df.contract == 0))
    df["churn"] = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return df

Fixing tags after the fact

Forgot a tag, or used "NN" instead of "nn"? MlflowClient().set_tag(run_id, key, value) works on finished runs, so you can fix old runs in a loop. client.delete_tag(run_id, key) removes one. Metrics and parameters, by contrast, should be treated as a permanent record of what happened.

runs = mlflow.search_runs(experiment_names=["churn-week3"], filter_string="tags.model_family = 'NN'")
for run_id in runs["run_id"]:
    MlflowClient().set_tag(run_id, "model_family", "nn")

3Comparing runs

Intuition. mlflow.search_runs is a database query that returns a pandas DataFrame. Filter with tags, sort by a metric, and you have a leaderboard you can rebuild with one command after every new run.

Logging a set of runs to compare

This script logs seven runs into the same experiment: two logistic regressions, two random forests and two small neural networks (scikit-learn's MLPClassifier, trained one epoch at a time so we can log a curve, just like a Keras model). Every run gets the same tags, the same split and the same metrics.

# compare.py
import time
import numpy as np
import mlflow
from mlflow import MlflowClient
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
from sklearn.neural_network import MLPClassifier
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import train_test_split
from sklearn.metrics import accuracy_score, recall_score, f1_score
from common import make_churn_data

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("churn-week3")

df = make_churn_data()
X, y = df.drop(columns="churn"), df["churn"]
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, stratify=y, random_state=42)

def log_scores(model):
    pred = model.predict(X_test)
    mlflow.log_metrics({
        "train_accuracy": accuracy_score(y_train, model.predict(X_train)),
        "test_accuracy": accuracy_score(y_test, pred),
        "test_recall": recall_score(y_test, pred),
        "test_f1": f1_score(y_test, pred),
    })

COMMON = {"dataset_version": "churn-v2", "author": "samuel", "stage": "experiment"}

for C in [0.1, 1.0]:
    with mlflow.start_run(run_name=f"logreg-C{C}", tags={**COMMON, "model_family": "ml", "algorithm": "logistic_regression"}):
        model = make_pipeline(StandardScaler(), LogisticRegression(C=C, max_iter=1000))
        t0 = time.perf_counter(); model.fit(X_train, y_train)
        mlflow.log_params({"C": C})
        mlflow.log_metric("train_seconds", time.perf_counter() - t0)
        log_scores(model)

for depth in [6, None]:
    with mlflow.start_run(run_name=f"rf-depth{depth}", tags={**COMMON, "model_family": "ml", "algorithm": "random_forest"}):
        model = RandomForestClassifier(n_estimators=200, max_depth=depth, random_state=42, n_jobs=-1)
        t0 = time.perf_counter(); model.fit(X_train, y_train)
        mlflow.log_params({"n_estimators": 200, "max_depth": depth})
        mlflow.log_metric("train_seconds", time.perf_counter() - t0)
        log_scores(model)
        mlflow.sklearn.log_model(model, name="model",
                                 skops_trusted_types=["sklearn.tree._tree.Tree"])

# Small neural networks trained epoch by epoch so we can log a curve
for width in [16, 64]:
    with mlflow.start_run(run_name=f"mlp-{width}", tags={**COMMON, "model_family": "nn", "algorithm": "mlp"}):
        scaler = StandardScaler().fit(X_train)
        Xtr, Xte = scaler.transform(X_train), scaler.transform(X_test)
        net = MLPClassifier(hidden_layer_sizes=(width,), learning_rate_init=0.01, random_state=42)
        mlflow.log_params({"hidden_units": width, "epochs": 15})
        t0 = time.perf_counter()
        for epoch in range(15):
            net.partial_fit(Xtr, y_train, classes=[0, 1])
            mlflow.log_metric("val_accuracy", accuracy_score(y_test, net.predict(Xte)), step=epoch)
        mlflow.log_metric("train_seconds", time.perf_counter() - t0)
        model = make_pipeline(scaler, net)
        log_scores(model)
print("logged", len(mlflow.search_runs(experiment_names=["churn-week3"])), "runs")

Gotcha: "references untrusted types". In MLflow 3.17, mlflow.sklearn.log_model saves scikit-learn models in the safer skops format, which refuses to save object types it hasn't been told are safe. For any tree-based model (decision tree, random forest, extra trees, gradient boosting) you get:

MlflowException: The saved sklearn model references untrusted types. If you are sure loading these
types is safe, set the 'skops_trusted_types' parameter when calling 'log_model' or 'save_model' to the
list of trusted types. Root error: Untrusted types found in the file: ['sklearn.tree._tree.Tree'].

The fix is the one used above: pass skops_trusted_types=["sklearn.tree._tree.Tree"]. If the error names other types, add those to the list too (only for models you trained yourself).

Filter syntax

A filter_string is a small SQL-like condition. Each condition has three parts: what (with a prefix), a comparison, and a value.

PrefixValue typeComparisons allowedExample
metrics.Number, no quotes= != > >= < <=metrics.test_f1 >= 0.84
params.Text, in quotes= != LIKE ILIKEparams.C = '0.1'
tags.Text, in quotes= != LIKE ILIKEtags.model_family = 'nn'
attributes.Run fields: status, run_name, start_time…Depends on the fieldattributes.status = 'FINISHED'
  • Combine conditions with and (or AND). There is no or: run two searches and pd.concat them.
  • LIKE is a pattern match: % means "anything", _ means "one character". ILIKE is the same but ignores upper/lower case. Example: tags.mlflow.runName LIKE 'rf-%'.
  • Parameters are stored as text, so params.max_depth = 'None' works but params.max_depth > 5 does not. If you need to compare a setting numerically, also log it as a metric.
  • A run that doesn't have the key (say, no test_recall metric) simply doesn't match.

These are the real error messages from MLflow 3.17.1 for the commonest mistakes:

You wroteMLflow says
tags.model_family = mlParameter value is either not quoted or unidentified quote types used for string value ml. Use either single or double quotes.
metrics.test_f1 > '0.6'Expected numeric value type for metric. Found '0.6'
tags.model_family = 'ml' or tags.model_family = 'nn'Invalid clause(s) in filter string: 'or'
tags.stage IN ('baseline', 'experiment')Expected a quoted string value for tag (e.g. 'my-value'). Got value ('baseline', 'experiment')

Searching, sorting and building a comparison table

# search.py
import mlflow
from mlflow import MlflowClient
mlflow.set_tracking_uri("sqlite:///mlflow.db")

runs = mlflow.search_runs(
    experiment_names=["churn-week3"],
    filter_string="tags.model_family = 'ml' and metrics.test_accuracy > 0.7",
    order_by=["metrics.test_accuracy DESC"],
)
print(len(runs), "matching runs")

cols = ["tags.mlflow.runName", "tags.algorithm", "metrics.train_accuracy",
        "metrics.test_accuracy", "metrics.test_recall", "metrics.train_seconds"]
table = runs[cols].rename(columns=lambda c: c.split(".")[-1])
table["gap"] = table["train_accuracy"] - table["test_accuracy"]
print(table.round(3).to_string(index=False))

Read the table, not just the top row. The unlimited-depth forest scores 100% on training data and has the biggest train–test gap (0.179): it is overfitting. The baseline run from tagging.py has NaN (missing) for the metrics it never logged, which is why every run should log the same metrics. Your train_seconds will differ.

order_by takes a list, so you can sort by several columns: order_by=["tags.model_family ASC", "metrics.test_f1 DESC"].

When nothing matches

# A filter that matches nothing returns an EMPTY DataFrame with NO metrics/params/tags columns
empty = mlflow.search_runs(experiment_names=["churn-week3"],
                           filter_string="tags.algorithm = 'xgboost'")

    print("No runs matched - check the filter")
0 ['run_id', 'experiment_id', 'status', 'artifact_uri', 'start_time', 'end_time']
No runs matched - check the filter

Always check len(df) before indexing. An empty result has none of the metrics.*, params.* or tags.* columns, so empty["metrics.test_f1"] raises a KeyError, and empty.iloc[0] raises an IndexError. The usual cause is a typo in a tag value or the wrong experiment name.

Metric history: the whole epoch curve

A metric column in search_runs holds only the last value logged. For the full curve, ask the client for the history:

# Per-epoch curve of the best neural network
nn = mlflow.search_runs(experiment_names=["churn-week3"],
                        filter_string="tags.model_family = 'nn'",
                        order_by=["metrics.test_f1 DESC"], max_results=1)
history = MlflowClient().get_metric_history(nn.loc[0, "run_id"], "val_accuracy")
for m in history[:3]:
    print(m.step, round(m.value, 3))
best_epoch = max(history, key=lambda m: m.value)
print("best epoch:", best_epoch.step, round(best_epoch.value, 3))
0 0.832
1 0.833
2 0.829
best epoch: 13 0.838

Each item has .step, .value and .timestamp. Turn it into a DataFrame (pd.DataFrame([(m.step, m.value) for m in history])) to plot several runs' curves on one chart.

Comparing in the UI

Start the UI from the folder that contains mlflow.db:

uv run mlflow ui --backend-store-uri sqlite:///mlflow.db
# then open http://127.0.0.1:5000  (add --port 5001 if 5000 is busy)
  1. Pick the experiment in the left-hand list. Type a filter string into the search box above the runs table: it uses exactly the same syntax as search_runs.
  2. Choose columns: add the tags and metrics you care about (model_family, test_f1, train_seconds) so the table becomes your leaderboard. Click a column header to sort.
  3. Tick two or more runs and click "Compare". The compare page shows parameters and metrics side by side, with differences highlighted.
  4. Parallel coordinates plot: each run is a line crossing vertical axes, one per parameter and one for a metric. It shows at a glance which settings lead to the good scores (for example, all the best lines pass through low max_depth).
  5. Scatter and contour plots show one parameter against a metric; metric charts overlay per-epoch curves (val_accuracy by step) for the selected runs.
  6. The chart view of the experiment page draws bar and line charts for many runs at once, which is handy for presentations.

4What makes a fair comparison

Intuition. A leaderboard is only meaningful if every model sat the same exam, under the same rules, and the difference between them is bigger than luck.

RequirementWhyHow
Same splitA model tested on easier rows looks better without being betterFix random_state in train_test_split, or save the test row IDs; tag runs with dataset_version
Same metrics, same definitions"F1" with a 0.5 threshold and "F1" with a tuned threshold are different numbersOne shared log_scores() function used by every run
Same preprocessing rulesScaling fitted on all data leaks test information into one model but not anotherPut preprocessing inside a pipeline fitted on training rows only
Look at the train–test gapA big gap means overfitting, so the test score is less trustworthy on new dataLog train_* and test_* metrics; compute the gap in your table
Training time and prediction speedA model that is 0.2 points better but 50× slower may not be worth itLog train_seconds; time predict on 1,000 rows
Model sizeBig models cost more to store, load and serveLog the saved file size, or the number of parameters for a network
Noise on small test setsAccuracy on a few hundred rows jumps around by several points from luck aloneUse cross-validation, several seeds, or a promotion margin

How big is "luck"?

For accuracy p measured on n test rows, the standard error (the typical size of the random wobble) is about √(p(1 − p) / n). Roughly 95% of the time, the true accuracy lies within ±2 standard errors.

Test rows (n)Accuracy 0.80, ± aboutSo a difference of…
200±5.5 points3 points between two models could easily be luck
1,000±2.5 points1 point is still within the noise
10,000±0.8 points1 point starts to be believable

That is why the promotion rule in section 6 asks the challenger to win by a margin, not just by any amount. When two models score within the noise, prefer the simpler, faster, cheaper one.

5The model registry

Intuition. Runs are the lab notebook; the registry is the shelf of finished products. Each product has numbered versions, and movable labels (aliases) say which version is in use right now.

TermMeaningExample
Registered modelA named entry on the shelfchurn-classifier
VersionA numbered, frozen copy of a logged model, linked to the run that produced it. Numbers only go up and are never reusedVersion 1, 2, 3…
AliasA named pointer to exactly one version. Moving it is instant; loading code doesn't change@champion → version 2
Version tagA key = value note on one versionvalidation_status = approved, dataset_version = 2026-06
DescriptionFree text on a version or on the registered model"RF depth 6, trained on churn-v2"

Why aliases replaced stages

Older MLflow had fixed stages: each version was in exactly one of None, Staging, Production or Archived, moved with transition_model_version_stage. Stages are now deprecated. Aliases do the same job better:

  • You choose the names: champion, challenger, previous_champion, shadow, eu-production…
  • A version can carry several aliases, and each alias points at exactly one version, so there is never any doubt about which model "production" means.
  • Moving an alias is one call, and every program that loads models:/churn-classifier@champion picks up the new version next time it loads.
  • Workflow states such as "approved" go in version tags instead of stages.

Register, tag, alias, load and roll back

# registry.py  (run compare.py first: it logs the random-forest models)
import mlflow
from mlflow import MlflowClient
mlflow.set_tracking_uri("sqlite:///mlflow.db")
NAME = "churn-classifier"
client = MlflowClient()

# Find the run of the best random forest (it has a logged model)
rf = mlflow.search_runs(experiment_names=["churn-week3"],
                        filter_string="tags.algorithm = 'random_forest'",
                        order_by=["metrics.test_f1 DESC"], max_results=1)
run_id = rf.loc[0, "run_id"]

mv = mlflow.register_model(f"runs:/{run_id}/model", NAME)
print("registered", mv.name, "version", mv.version, "source", mv.source)

# Version tags and a description
client.set_model_version_tag(NAME, mv.version, "validation_status", "approved")
client.update_model_version(NAME, mv.version, description="RF depth 6, trained on churn-v2")
client.set_registered_model_alias(NAME, "champion", mv.version)

champ = client.get_model_version_by_alias(NAME, "champion")
print("champion is version", champ.version, champ.tags)

model = mlflow.pyfunc.load_model(f"models:/{NAME}@champion")
from common import make_churn_data
X = make_churn_data(5, seed=9).drop(columns="churn")
print(model.predict(X))

# Register a second version from the other RF run, then roll back
rf2 = mlflow.search_runs(experiment_names=["churn-week3"],
                         filter_string="tags.mlflow.runName = 'rf-depthNone'")
mv2 = mlflow.register_model(f"runs:/{rf2.loc[0, 'run_id']}/model", NAME)
client.set_registered_model_alias(NAME, "champion", mv2.version)
client.set_registered_model_alias(NAME, "previous_champion", mv.version)
print("champion now", client.get_model_version_by_alias(NAME, "champion").version)
# Roll back: move the alias back
client.set_registered_model_alias(NAME, "champion", mv.version)
print("after rollback", client.get_model_version_by_alias(NAME, "champion").version)
print(client.get_registered_model(NAME).aliases)

6Champion vs challenger

Intuition. The champion holds the title until a challenger beats it in a fair fight, on the same ground, by a clear margin, without breaking any rules. A draw goes to the champion.

Champion

The model currently serving predictions. In the registry it is the version with the @champion alias.

Challenger

A newly trained candidate (new data, new features, new algorithm). It gets the @challenger alias while it is being evaluated.

The promotion rule

Write the rule down before you see the results, so nobody is tempted to move the goalposts. A good rule has four parts:

PartExampleWhy
Same holdout dataBoth models scored on the same recent rows that neither trained onOtherwise you compare exams, not students
Primary metric beats the champion by a marginROC-AUC (challenger) ≥ ROC-AUC (champion) + 0.01Small differences are noise (section 4); swapping models has a cost
No regression on guard-rail metricsRecall (or F1) must not drop by more than 0.02A model can win on one number while getting worse at the thing the business cares about most
Operational limitsPrediction time ≤ 50 ms per 1,000 rows; model file ≤ 200 MBA model that is too slow or too big can't be served

Beyond an offline holdout: shadow and A/B testing

Shadow deployment

The challenger receives a copy of real live requests and makes predictions, but its answers are only logged, never used. Safe, and it tests speed and behaviour on real traffic. Once labels arrive you can score it.

A/B test (canary)

A small share of real traffic (say 5–10%) is actually served by the challenger, and the business outcome (retention, revenue, complaints) is compared between the two groups. More realistic, but real customers are exposed to the new model.

"""evaluate.py - score champion and challenger on the same holdout, write results to JSON."""
import argparse, json
import mlflow
from sklearn.metrics import roc_auc_score, f1_score
from common import make_churn_data

def score(uri, X, y):
    proba = mlflow.sklearn.load_model(uri).predict_proba(X)[:, 1]
    return {"roc_auc": roc_auc_score(y, proba), "f1": f1_score(y, (proba >= 0.5).astype(int))}

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--config", default="config.json")
    parser.add_argument("--drift", type=float, default=0.0)

"""promote.py - apply the promotion rule and move the aliases."""
import argparse, json
import mlflow
from mlflow import MlflowClient

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--config", default="config.json")
    args = parser.parse_args()
    cfg = json.load(open(args.config))
    rule = cfg["promotion"]
    mlflow.set_tracking_uri(cfg["tracking_uri"])
    client, name = MlflowClient(), cfg["model_name"]

    res = json.load(open("eval_results.json"))
    champ, chall = res["champion"], res["challenger"]
    m = rule["primary_metric"]
    promote = (chall[m] >= champ[m] + rule["margin"]
               and chall["f1"] >= champ["f1"] - rule["max_f1_drop"])

    old = client.get_model_version_by_alias(name, "champion").version
    new = client.get_model_version_by_alias(name, "challenger").version
    if promote:
        client.set_registered_model_alias(name, "previous_champion", old)
        client.set_registered_model_alias(name, "champion", new)
        print(f"promoted v{new} (was v{old})")
    else:
        print(f"kept v{old}; v{new} did not win")
    client.delete_registered_model_alias(name, "challenger")

if __name__ == "__main__":
    main()

9Drift

Intuition. A model is a snapshot of the world at training time. Drift is the world moving on: different customers arrive (data drift), or the same kind of customer now behaves differently (concept drift).

TypeWhat changesIn symbolsChurn exampleDetect with
Data drift (covariate shift)The distribution of the inputsP(X) changes, P(y | X) the sameA price rise: monthly charges are now £85 on average instead of £60PSI, KS, chi-square on features; no labels needed
Concept drift (model drift)The relationship between inputs and targetP(y | X) changesA competitor targets loyal customers: long tenure no longer protects against churnPerformance on labelled recent data; sometimes prediction drift
Prediction driftThe distribution of the model's outputsP(ŷ) changesThe model flags 55% as churners instead of 30%PSI or KS on the scores
Label drift (prior shift)How common each class isP(y) changesOverall churn rises from 20% to 35%Compare class shares once labels arrive

How drift shows up over time

  • Sudden: a new law, a price change, a new app version. Performance drops overnight.
  • Gradual: customer habits slowly change; the model decays a little each week.
  • Seasonal / recurring: December looks different from June every year. Not really drift if the training data covers whole years; a reason to compare like with like (this December against last December).

Data drift doesn't always hurt, and concept drift can't be seen without labels. If customers shift into a region where the model is still right, performance holds. And in the worked example below, the inputs tenure_months and age show no drift at all, yet the meaning of tenure has changed completely. Only labelled recent data reveals that. Monitor both inputs and performance.

The detection recipe

  1. Keep a reference window: usually the training data (or a sample of it, saved as an artifact with the model).
  2. Collect a current window: the last day, week or N requests seen by the live model.
  3. For each feature (and for the predictions), compare the two distributions with PSI and a statistical test.
  4. When labels arrive, compute the real metrics on the current window and compare them with the evaluation metrics at training time.
  5. Alert when a threshold is crossed; investigate; retrain if needed.

Population stability index (PSI)

PSI measures how far a distribution has moved in one number. Cut the feature into bins using the reference data (often 10 bins with equal counts), work out what percentage of rows fall in each bin in both windows, and add up:

PSI = Σ over bins (cur% − ref%) × ln(cur% / ref%)

Each term is never negative: if a bin's share grows, both factors are positive; if it shrinks, both are negative. So PSI is 0 when the distributions match and grows as they diverge. Percentages are written as fractions (10% = 0.10). An empty bin would mean dividing by zero or taking ln(0), so code replaces zeros with a tiny number such as 0.0001.

0.1 – 0.25moderate shiftInvestigate; watch closely
> 0.25significant shiftAlert; check performance; consider retraining

Statistical tests: KS and chi-square

Kolmogorov–Smirnov (KS) test: numeric features

Compares two samples' cumulative distributions and finds the biggest vertical gap between them (the KS statistic, 0 to 1). The p-value answers "if nothing had changed, how likely is a gap this big?". A small p-value (say < 0.05) means the difference is unlikely to be chance. scipy.stats.ks_2samp(ref, cur).

Chi-square test: categorical features

Counts each category in both windows and checks whether the proportions differ more than chance would allow. Build a table of counts (window × category) and pass it to scipy.stats.chi2_contingency, which returns the statistic and a p-value.

p-values shout when the sample is big. With thousands of rows, a test will flag a difference far too small to matter. In the example below, contract has a chi-square p-value of essentially 0 but a PSI of only 0.0998. Use the test to ask "is it real?" and PSI (or the KS statistic) to ask "is it big?". Alert on size, not on the p-value alone.

# drift.py
import numpy as np
import pandas as pd
from scipy.stats import ks_2samp, chi2_contingency

def psi(reference, current, bins=10, eps=1e-4):
    """Population stability index of one numeric feature."""
    edges = np.unique(np.quantile(reference, np.linspace(0, 1, bins + 1)))
    edges[0], edges[-1] = -np.inf, np.inf            # catch values outside the old range
    ref_pct = np.histogram(reference, edges)[0] / len(reference)
    cur_pct = np.histogram(current, edges)[0] / len(current)
    ref_pct, cur_pct = np.clip(ref_pct, eps, None), np.clip(cur_pct, eps, None)  # avoid log(0)
    return float(np.sum((cur_pct - ref_pct) * np.log(cur_pct / ref_pct)))

def psi_label(value):
    return "stable" if value < 0.1 else "moderate" if value < 0.25 else "significant"

def drift_report(ref_df, cur_df, numeric, categorical):
    rows = []
    for col in numeric:
        p = psi(ref_df[col], cur_df[col])
        ks = ks_2samp(ref_df[col], cur_df[col])
        rows.append({"feature": col, "psi": p, "psi_level": psi_label(p),
                     "test": "KS", "p_value": ks.pvalue})
    for col in categorical:
        counts = pd.crosstab(np.r_[np.zeros(len(ref_df)), np.ones(len(cur_df))],
                             np.r_[ref_df[col], cur_df[col]])
        chi2, p_value, dof, _ = chi2_contingency(counts)
        p = psi(ref_df[col], cur_df[col])
        rows.append({"feature": col, "psi": p, "psi_level": psi_label(p),
                     "test": "chi-square", "p_value": p_value})
    return pd.DataFrame(rows)

Notes on the code: bin edges come from the reference quantiles, so each reference bin holds about 10% of rows; np.unique merges duplicate edges, which happen for features with few distinct values (such as contract, where each value then gets its own bin); the outer edges are widened to ±infinity so new extreme values are still counted.

Drift tools

You can build monitoring yourself with the functions above. Dedicated libraries add ready-made reports, dashboards and many more tests: Evidently (open source, HTML drift reports), NannyML (open source, can estimate performance before labels arrive) and WhyLabs (hosted monitoring platform). They are worth knowing by name; on this course, PSI plus KS and chi-square is enough.

10Retraining strategies

Intuition. Retraining answers three questions: when do we retrain, on which data, and how do we decide the new model is allowed to replace the old one. The answer to the third is always "as a challenger".

When: scheduled or triggered

StrategyHow it worksStrengthsWeaknesses
ScheduledRetrain every week / month, whatever happensSimple, predictable; catches slow driftWastes compute when nothing changed; too slow for sudden drift
Triggered by driftRetrain when PSI (or a test) crosses a thresholdReacts early, before labels arriveData drift doesn't always hurt, so some retrains are unnecessary
Triggered by performanceRetrain when a real metric drops below a thresholdResponds to actual harm, including concept driftLate: you need labels, so the damage is already done
Hybrid (common in practice)A schedule plus triggers, with a cooldown so one problem doesn't start ten retrainsBalancedMore to configure

On which data

WindowWhat it meansWhen to use it
Sliding windowOnly the most recent N weeks or monthsThe world has changed and old data now teaches the wrong lesson (concept drift)
Expanding window (all data)Everything collected so farThe world is stable and more data simply helps; rare events need every example
WeightedAll data, with recent rows weighted more (sample_weight in fit)A compromise between the two

Whatever the window, the holdout used to compare champion and challenger must come from the most recent period and must not be used for training: that is the data the model will face next.

How: never blind replacement

Never let a freshly trained model overwrite the champion automatically. New data can be broken (a bug upstream, a missing column filled with zeros), and a model trained on it can be worse than the one in production. Every retrain produces a challenger that must pass the same promotion rule as in section 6. A rejected challenger is a useful signal too: maybe the drift isn't learnable from the data you have, and a human needs to look.

Have a rollback plan

  • Keep the previous champion registered, with the previous_champion alias.
  • Make rollback one command: client.set_registered_model_alias(NAME, "champion", previous_version), then reload the model in the API (restart it, or call a reload endpoint).
  • Decide in advance what triggers a rollback: error rate, latency, a business metric, a complaint.
  • Log every promotion and rollback as an MLflow run with tags (decision, versions, reason), so you can always answer "which model was live on 3 March, and why?".

Try it: the MLOps loop simulator

MLOps loop simulator
Each week a new batch of data arrives (simulated with a fixed random seed). The world drifts at the speed you choose. The pipeline measures PSI against the champion's training data and the champion's live accuracy; when a trigger fires it trains a challenger, scores both on the same recent holdout and applies the margin rule. A triggered retrain is followed by a 2-week cooldown.

    11Worked example: drift, retrain, challenge, promote

    Intuition. The whole loop in one script: a champion trained on last year's customers meets this year's customers, the pipeline notices, trains a challenger on recent data, and promotes it only because it wins fairly.

    Put common.py (section 2) and drift.py (section 9) in the same folder, then run uv run python pipeline.py. Start from an empty folder (or delete mlflow.db) so the version numbers match the output below.

    # pipeline.py
import time
import mlflow
from mlflow import MlflowClient
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split
from sklearn.metrics import accuracy_score, f1_score, recall_score, roc_auc_score
from common import make_churn_data
from drift import drift_report

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("churn-pipeline")
client = MlflowClient()
NAME = "churn-classifier"
FEATURES = ["tenure_months", "monthly_charges", "support_calls", "age", "contract"]

def evaluate(model, X, y):
    """Score one model on one dataset. Same function for champion and challenger."""
    t0 = time.perf_counter()
    proba = model.predict_proba(X)[:, 1]
    ms_per_1k = (time.perf_counter() - t0) / len(X) * 1_000_000
    pred = (proba >= 0.5).astype(int)
    return {"roc_auc": roc_auc_score(y, proba), "accuracy": accuracy_score(y, pred),
            "f1": f1_score(y, pred), "recall": recall_score(y, pred), "ms_per_1k_rows": ms_per_1k}

def train_and_register(X, y, run_name, tags):
    with mlflow.start_run(run_name=run_name, tags=tags):
        params = {"n_estimators": 200, "max_depth": 6, "random_state": 42}
        model = RandomForestClassifier(**params, n_jobs=-1).fit(X, y)
        mlflow.log_params(params)
        mlflow.log_metric("train_rows", len(X))
        info = mlflow.sklearn.log_model(model, name="model", input_example=X.iloc[:5],
                                        skops_trusted_types=["sklearn.tree._tree.Tree"])
    mv = mlflow.register_model(info.model_uri, NAME)
    client.set_model_version_tag(NAME, mv.version, "dataset_version", tags["dataset_version"])
    return mv

def load(alias):
    # the sklearn flavour gives back the real model, so predict_proba is available
    return mlflow.sklearn.load_model(f"models:/{NAME}@{alias}")

def show(label, metrics):
    print(label, {k: round(v, 3) for k, v in metrics.items() if k != "ms_per_1k_rows"})

    Step 1: the champion, trained on old data

    # ---- Step 1: champion v1, trained on the "old" data --------------------------
old = make_churn_data(6000, seed=1, drift=0.0)
old_train, old_holdout = train_test_split(old, test_size=0.25, stratify=old.churn, random_state=42)
v1 = train_and_register(old_train[FEATURES], old_train.churn, "train-v1",
                        {"dataset_version": "2026-01", "candidate": "champion"})
client.set_registered_model_alias(NAME, "champion", v1.version)
show("v1 on old holdout:   ", evaluate(load("champion"), old_holdout[FEATURES], old_holdout.churn))

    Step 2: new data arrives; check it for data drift

    # ---- Step 2: new data arrives; check it for data drift ----------------------
new = make_churn_data(4000, seed=2, drift=0.8)
report = drift_report(old_train, new, numeric=FEATURES[:4], categorical=["contract"])
print(report.round(4).to_string(index=False))
drifted = report.loc[report.psi >= 0.25, "feature"].tolist()
print("drifted features:", drifted)

    Step 3: labels arrive; measure the champion on recent data

    # ---- Step 3: labels arrive; measure the champion on recent data -------------
recent_train, recent_holdout = train_test_split(new, test_size=0.3, stratify=new.churn, random_state=42)
live = evaluate(load("champion"), recent_holdout[FEATURES], recent_holdout.churn)
show("v1 on recent holdout:", live)

    Steps 4–5: retrain a challenger and run the contest

    # ---- Step 4: retrain a challenger if drift or a performance drop ------------
if drifted or live["roc_auc"] < 0.80:
    v2 = train_and_register(recent_train[FEATURES], recent_train.churn, "train-v2",
                            {"dataset_version": "2026-06", "candidate": "challenger",
                             "trigger": "drift" if drifted else "performance"})
    client.set_registered_model_alias(NAME, "challenger", v2.version)

    # ---- Step 5: same holdout, same metrics, a margin and guard-rails -------
    champ_m = evaluate(load("champion"), recent_holdout[FEATURES], recent_holdout.churn)
    chall_m = evaluate(load("challenger"), recent_holdout[FEATURES], recent_holdout.churn)
    MARGIN, MAX_F1_DROP, MAX_MS = 0.01, 0.02, 50.0
    checks = {
        "beats_by_margin": chall_m["roc_auc"] >= champ_m["roc_auc"] + MARGIN,
        "f1_not_worse": chall_m["f1"] >= champ_m["f1"] - MAX_F1_DROP,
        "fast_enough": chall_m["ms_per_1k_rows"] <= MAX_MS,
    }
    promote = all(checks.values())

    with mlflow.start_run(run_name="champion-vs-challenger"):
        mlflow.log_metrics({f"champion_{k}": v for k, v in champ_m.items()})
        mlflow.log_metrics({f"challenger_{k}": v for k, v in chall_m.items()})
        mlflow.set_tags({"champion_version": v1.version, "challenger_version": v2.version,
                         "decision": "promote" if promote else "reject"})
    show("champion:  ", champ_m)
    show("challenger:", chall_m)
    print("checks:", checks, "-> promote" if promote else "-> keep champion")

    if promote:
        client.set_registered_model_alias(NAME, "previous_champion", v1.version)
        client.set_registered_model_alias(NAME, "champion", v2.version)
        client.delete_registered_model_alias(NAME, "challenger")
        client.set_model_version_tag(NAME, v2.version, "promoted_from", f"v{v1.version}")

    Step 6: the registry afterwards

    # ---- Step 6: the registry afterwards -----------------------------------------
print("aliases:", client.get_registered_model(NAME).aliases)
for v in client.search_model_versions(f"name = '{NAME}'", order_by=["version_number ASC"]):
    print(f"version {v.version}  tags={v.tags}")

    Reading the result

    • Data drift was detected on monthly_charges (PSI 1.75) and support_calls (0.60), with no labels needed. tenure_months and age are stable.
    • The champion collapsed on recent data: ROC-AUC fell from 0.913 to 0.638, accuracy from 0.835 to 0.568. Part of that is concept drift on tenure, which no input check could have seen.
    • The challenger won fairly: same recent holdout, ROC-AUC 0.798 vs 0.638 (far above the 0.01 margin), and F1 did not drop, so it was promoted. Version 1 keeps the previous_champion alias for rollback.
    • Why F1 and not recall as the guard-rail here? The drifted champion predicts "churn" for most customers, so its recall (0.877) is inflated by sheer volume of alarms, with poor precision. A recall guard-rail would have blocked a much better model. Choose guard-rails that match the business cost, and look at the whole picture before trusting any single number.
    • Even the new champion (0.798) is below the old champion's best (0.913): the new world is harder to predict from these features. That's a finding to report, not something retraining can fix.

    Next: serve models:/churn-classifier@champion behind an API in Serving models with FastAPI. Because the API loads by alias, the promotion above needs no code change in the service, only a reload.

    The loop in one sentence: tag every run consistently → compare on the same split with the same metrics → register the winner and alias it @champion → serve by alias → monitor health, inputs, predictions and (when labels come) performance → when drift or decay crosses a threshold, train a challenger on recent data → promote only if it beats the champion on the same recent holdout by a margin without breaking guard-rails → keep the old version for rollback.
